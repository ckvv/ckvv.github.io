# 高质量技术博客写作规范

## 一、核心目标

写清楚一个技术问题的机制、代价和适用边界，而不是复述文档。读者读完应该能解释某个现象、复现某个步骤，或判断某个方案在什么条件下不成立。默认读者是具备开发基础的工程师。

准确性是硬约束，篇幅不是：短而有据优于长而空洞。

## 二、准确性与证据

涉及可能变化的行为（API、默认值、性能数字、工具输出），写明版本或时间。

每个非显然的结论都要有一个作者能去核对的锚点，形式随文章而定：文档章节或 URL、源码仓库的路径与符号、一条命令及其真实输出、一次测量及测量方式与时间。没有锚点的结论删掉，而不是加限定词软化。

数字只有三种来源，文章要说明是哪一种：别处写明的（注明出处）、作者或工具实测的（注明方法与时间）、引用来源的（注明来源）。不把算出来的数写成观测值。

代码从真实来源复制并注明文件或生成它的命令，否则明确标为示意或伪代码。不声称未执行的代码已验证。案例、踩坑经历、引用来源同样不得虚构。

区分已验证事实、合理推断和个人建议；无法确认时就说不确定，或删掉该段。

## 三、内容价值

- 至少有一个来源没有给出的内容：一个结论、一次同条件对比、一个失败模式或一条边界条件。只把官方文档重新排版的文章不用写。
- 解释原因而不只是现象：设计为什么这样、代价是什么、换一个维度（性能、复杂度、维护成本）会怎样。
- 方案对比要有统一的比较维度，两边用相同的测量方式；给出带条件的选择建议，而不是"都能用"。
- 说明适用边界和失效条件。反例通常比最佳实践更有信息量。
- 笔记、链接汇总类文章在标题或 `description` 里说明自己是汇总，写明所汇总内容的版本或日期，不要包装成分析。

## 四、结构与表达

- 开头给问题、例子或结论。删掉复述标题的铺垫段和领域背景介绍，也不用"随着技术的快速发展"开场。
- 章节篇幅不均匀：有证据的地方展开，其余压缩。不为凑齐结构加章节，也不为每个小概念建一个小标题。
- 标题反映实际内容，不用比喻和夸张。
- 一个段落围绕一个观点。过程适合步骤，多方案对比适合表格，机制解释用连贯文字而不是列表。
- 结尾回答开头提出的问题，不逐节复述小结。
- 语言具体：写"少了一次回表"，不写"性能显著提升"。不用强大、优雅、先进、完美、丝滑、赋能、一站式、seamless、powerful；不用 emoji 和感叹号；不用"众所周知""显而易见"；不用"首先、其次、最后"串联全文；不用设问代替分析；不写"希望对你有帮助"。
- 代码保留理解所需的上下文，解释为什么这样写，不逐行翻译。图表用于说清关系，不用于填充版面。

## 五、文章类型

先定一个主类型，其他类型的要求按需取用。

| 类型 | 必须做到 | 典型失败 |
|---|---|---|
| 教程 | 前置知识、连续可执行的步骤、预期输出 | 只有代码没有解释；基础教程里塞底层细节 |
| 原理解析 | 从现象切入，讲机制与设计原因，指出限制 | 停在概念介绍；无必要的逐行源码讲解 |
| 方案对比 | 明确问题、统一维度、区分客观差异与主观体验 | 罗列功能清单；无证据的"全面优于" |
| 工程实践 | 问题背景、约束、候选方案、验证结果 | 把设计推演写成真实上线经历 |
| 技术观点 | 观点、成立条件、证据、反方情况 | 用个人偏好代替论证 |
| 源码分析 | 仓库与版本、入口与调用链、关键代码与设计原因 | 大段粘贴源码；分析与主题无关的模块 |

没有真实实践时，把文章定位为方案设计或示例实现，不写成项目经验。

## 六、写作流程

1. 调研：先确认 API、默认行为和版本差异，再决定文章要回答什么问题。
2. 提纲：确定核心问题，写出每节要回答的问题，删掉与目标无关的部分。
3. 正文：先写清问题和机制，再补例子、代码和边界。
4. 核查：逐条检查数字、因果句（因为/所以/因为这样才）和代码是否与实际一致；无法确认的核实、删掉或标为不确定。

有未确认内容时写成 `> TODO(verify): ...`，并把 frontmatter 设为 `draft: true`，确认后再发布。

## 七、优先级

准确性 > 内容价值 > 逻辑 > 深度与证据 > 结构与表达 > 排版。冲突时按这个顺序取舍：宁可留下可见的缺口，也不要用流畅的段落把它盖住。
